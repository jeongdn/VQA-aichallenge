# E18 (제안 번호) — Qwen3.5-122B-A10B zero-shot: Qwen 공식 GPTQ-Int4 · vLLM (2026-09-27)

## 왜
- Qwen3.5-122B-A10B는 OCRBench 92.1로 후보 중 1위다. 하지만 bf16이 244GB라 모델 조사 때 제외했다.
- 질문: "남이 양자화해 둔 것(HF에 155개)은 못 쓰나?"
- 답: **추론(zero-shot)은 가능하고 LoRA 학습은 불가능하다.** 규칙상으로는 HF 공개 모델이라 문제없다. Flash-Next GGUF도 이미 같은 방식으로 썼다.

## 양자화 판을 학습에 못 쓰는 이유 (transformers 5.17 코드 확인)
- compressed-tensors 4bit(예: cyankiwi AWQ)를 불러오면 MoE 전문가 층을 `DecompressExperts`가 bf16으로 풀어 합친다. 전문가 층만 232GB가 그대로 남는다.
- GPTQ·AWQ·AutoRound·NVFP4 로더에는 합쳐진 3D 전문가 층을 다루는 코드가 없다. 전문가 층 처리 코드가 있는 것은 compressed-tensors, FP8, MXFP4(GPT-OSS 전용)뿐이다.
- bitsandbytes는 3D 파라미터를 양자화하지 못한다.
- Unsloth 문서도 122B-A10B bf16 LoRA에 256GB가 필요하고, MoE 4bit QLoRA는 권장하지 않는다고 적어 두었다.

## 형식 비교 (G4 96GB 한 장 기준)
| 형식 | 저장소 예 | 크기 | 판단 |
|---|---|---|---|
| GPTQ-Int4 (Qwen 공식) | `Qwen/Qwen3.5-122B-A10B-GPTQ-Int4` | 78.9GB. 전문가 층만 int4(그룹 128), 어텐션·공유 전문가·비전·임베딩은 bf16 | **채택**: vLLM `moe_wna16` (모델 카드 권장) |
| AWQ | `cyankiwi/...-AWQ-4bit` (compressed-tensors, 그룹 32) · `QuantTrio/...-AWQ` | cyankiwi 84.5GB | vLLM에서 가능. 공식 판보다 큼 |
| NVFP4 | `nvidia/...-NVFP4` · `unsloth/...-NVFP4` | 약 70GB | 활성값까지 4bit(W4A4)라 손실이 더 큼. Blackwell 전용 |
| FP8 (Qwen 공식) | `Qwen/...-FP8` | 약 125GB | 96GB에 안 들어감 |
| GGUF | `unsloth/...-GGUF` 등 (Q4_K_M 74GB + mmproj) | 약 74GB | llama.cpp로 가능하지만, 문항당 이미지 약 2,700토큰 × 7,714문항을 처리하기엔 느림 |
| MLX · EXL3 | mlx-community · turboderp | — | 애플 전용 / 이 파이프라인과 무관 |

## `zs122b_vllm.ipynb`
- **엔진**: vLLM 0.30.0(2026-09-22)과 transformers 5.17.0.
  - 드라이버가 CUDA 13을 지원하면 기본 휠을, 아니면 CUDA 12.9 휠을 설치한다.
  - Colab에 원래 있던 torchaudio(CUDA 12.8용)가 새 torch 2.13(CUDA 13)과 섞여 `AutoProcessor` import가 실패했다. vLLM도 `import torchaudio`에서 ImportError만 건너뛰므로 같은 오류가 난다.
    - 원인: vLLM 0.30이 의존성으로 PyPI판 torchaudio 2.11.0(CUDA 12.8용)을 같이 깐다. 그래서 새로 설치할 때마다 다시 생긴다.
    - 두 겹으로 막는다.
      1. 설치 셀이 매번 torchaudio를 지운다. vLLM은 모델 구조를 별도 프로세스(`python -m vllm.model_executor.models.registry`)에서 검사하므로, 지우지 않으면 거기서 `Model architectures [...] failed to be inspected`가 난다(세 번째 실행에서 발생).
      2. 1번 셀이 `sys.modules["torchaudio"] = None`으로 노트북 프로세스에서 '없는 것'으로 만든다. transformers는 `find_spec`이 None이라 건너뛰고, vLLM은 ImportError라 건너뛴다.
    - 오디오는 쓰지 않는다.
  - 설치 뒤 차단 없는 새 프로세스에서(vLLM 검사 프로세스와 같은 조건) torch·torchvision·transformers·vllm·`vllm.model_executor.models.qwen3_5`를 import해 보고 버전을 출력한다.
  - 엔진은 노트북 프로세스 안에서 돌린다(`VLLM_ENABLE_V1_MULTIPROCESSING=0`).
    - Colab의 출력 스트림에는 파일 번호가 없다. 그래서 vLLM이 분산 초기화 중 `suppress_stdout()`에서 `UnsupportedOperation: fileno`로 멈췄다(두 번째 실행). 파일 번호가 없을 때만 이 C 출력 숨기기 함수 세 곳을 빈 함수로 바꾼다. vLLM 0.30 소스에서 `sys.stdout.fileno()`를 부르는 곳은 이것 하나다.
  - vLLM은 가중치를 받을 때 진행 막대를 숨긴다(`DisabledTqdm`). 그래서 7-0 셀에서 `snapshot_download`로 먼저 받는다(79GB, 이어받기 가능).
  - 선형 어텐션(GDN) 커널은 `gdn_prefill_backend="triton"`으로 고정한다.
    - vLLM 기본값(auto)은 Blackwell(SM12x)에서 FlashInfer판을 고른다. 이 판은 CUTLASS 파이썬 DSL(`cutlass`)이 필요하다.
    - `nvidia-cutlass-dsl`은 `.pth` 파일로 경로를 추가하는 방식이라, 설치한 뒤 커널을 다시 시작하지 않으면 보이지 않는다.
    - 그래서 네 번째 실행에서 `No module named 'cutlass'`가 났다. FlashInfer 쪽 JIT 환경 경고("SM 12.x requires CUDA >= 12.9")도 있어 Triton판(A100 기본값과 같음)으로 피한다.
  - `VLLM_USE_FLASHINFER_SAMPLER=0`으로 둔다. 초기화 때 top-k/top-p 표본 추출을 FlashInfer JIT로 시험하는 단계를 피하려는 것이고, 채점은 그리디 1토큰이라 무관하다.
  - 네 번째 실행에서 확인된 실제 GPU 동작:
    - 가중치 68.16GiB(로드 38초), KV 캐시 15.13GiB(368,640토큰)
    - 전문가 층 Triton WNA16, 어텐션·비전 FlashAttention 2 정상
  - 설정: `enforce_eager`, 프리픽스 캐시 끔, `max_num_seqs` 16, 이미지 1장·영상 0.
- **다른 멤버와 같게 맞춘 것**
  - 분할(md5 `df05e4bc…`)
  - 프롬프트 `baseline_v1`: 시스템 지시 + 이미지 + 질문·보기, `enable_thinking=False`
  - 해상도 up2.0
  - 글자 변형 합산(a/A/␣a/␣A → 네 글자 정규화)
- **이미지 크기 미리 맞추기**
  - 5.17 `smart_resize`(32 배수) + bicubic antialias로 up2.0 크기에 맞춰 넘긴다.
  - vLLM 쪽 프로세서 범위는 (1,024, 상한×1.1)로 넓혀 다시 바꾸지 않게 한다.
  - 노트북이 검증 3장에서 두 경로의 픽셀·격자가 같은지 확인한다. 다르면 미리 맞추기를 끄고 stage2와 같은 경로로 돌린다.
  - 문항마다 이미지 토큰 수도 대조해 저장한다.
- **확률**: 답 자리 상위 64개 로그확률에서 모은다. 64개 안에 없는 글자는 0으로 두고 `n_missing`에 기록한다.
- **진행 순서**
  1. 검증 앞 300문항을 채점한다. 같은 문항에서 다른 zero-shot 기록·학습 멤버와 비교(고침/새로 틀림, 부호 검정)하고, E14 오답 24개 중 맞힌 것을 보인다.
  2. `GATE_ACC` 96.0% 이상이면 검증 나머지 700 + test 6,714로 넘어간다.
  3. 결과를 E14 이름으로 저장한다: `preds_final_ep1__up2.0__1000.csv`, `preds_final_ep1_test__up2.0__6714.csv`, `train_log.json`(MODEL_ID = 새 계열, `ZERO_SHOT: true`).
- **이어하기**: 64문항마다 Drive에 저장한다. 반쯤 쓴 줄은 버리고 다시 채점한다. 셀을 중간에 멈춰 엔진에 남은 이전 요청이 있으면 그 결과는 버린다.
- **첫 묶음 점검**: letter_mass 평균이 0.5 미만이면 최상위 토큰을 출력하고 멈춘다(템플릿·생각 모드 문제). 이미지 토큰 불일치는 경고만 한다.
- **실행 이름**: `vqa_runs/q35_122b_a10b_gptq_zs`

## 점검 (CPU)
- **미리 맞추기**: 실제 대회 사진 30장, 다른 사진 1장, 극단 비율·아주 작거나 큰 합성 10장.
  - 5.17 프로세서 경로와 pixel_values가 완전히 같다(최대 차이 0).
  - 이미지 토큰 수 = (h/32)·(w/32).
  - 대회 사진 720×960 → up2.0 1440×1920, 토큰 2,700.
- **노트북 전체 흐름**: 가짜 vLLM으로 9개 시나리오를 돌려 모두 통과했다.
  - 가짜 vLLM 구성:
    - 인자 이름을 실제 0.30.0 소스(LLM·EngineArgs·SamplingParams)와 대조한다.
    - 실제 vLLM처럼 HF 프로세서로 프롬프트와 이미지를 처리한다.
    - 프로세서는 실제 5.17 `Qwen3VLProcessor`에 작은 토크나이저를 붙인 것이다.
  - 시나리오:
    - auto(300 → 전체)
    - 셀을 멈춰 요청이 엔진에 남음
    - test 도중 중단 → 같은 세션에서 이어하기
    - 검증 도중 중단 → 새 세션에서 이어하기. 두 경우 모두 반쯤 쓴 줄 포함, 결과가 중단 없는 실행과 완전히 같음.
    - 기준 미달로 멈춤
    - quick
    - letter_mass 낮음 → 멈춤
    - 이미지 토큰 불일치 → 경고
    - 미리 맞추기 대조 실패 → 원본 경로로 전환
  - 검사 항목:
    - 확률·letter_mass를 가짜 vLLM 출력에서 독립 계산한 값과 대조
    - 누락 글자 = 0
    - E14 읽기 함수(E8/E14 노트북 코드 그대로)가 이 실행을 새 계열 멤버로 찾음
    - 비교 수치를 독립 계산과 대조. `_dry` 폴더와 문항이 모자란 파일은 제외
    - 단독 제출 파일 형식
- **설치 셀·torchaudio**: import하면 실제 실행과 같은 CUDA 불일치 RuntimeError를 내는 가짜 torchaudio로 확인했다.
  - 대조군 두 가지로 실제 실행 오류를 그대로 재현했다.
    - 차단이 없으면 `AutoProcessor` 오류가 난다.
    - 가짜 vLLM이 실제처럼 별도 프로세스에서 모델을 검사하게 하고 torchaudio를 남겨 두면 `failed to be inspected`가 난다.
  - 수정 뒤: 설치 셀이 지우고 점검을 통과한다. torchaudio가 남으면 다시 지우라는 안내와 함께 멈춘다. 노트북 전체 흐름(`badta` 시나리오)도 통과한다.
- **시험하지 못한 것**: 실제 GPU에서의 vLLM 동작(커널·메모리·속도). 노트북 7번 셀 표에 증상별 대처 설정이 있다.

## 판단
- 앞 300문항을 같은 문항 zero-shot과 비교한다: Q35-27B 96.33 · Qwen3.6-35B-A3B 96.33 · HCX 95.67 · Flash-Next IQ3_XXS 95.33 · Gemma4-31B 97.67.
- 학습을 못 하므로 zero-shot 그대로 멤버가 된다. 전체가 끝나면 E14가 자동으로 포함하고, 조합은 팀이 정한다.
