# E19 (제안 번호) — RunPod B300에서 Qwen3.5-122B-A10B bf16 LoRA (2026-09-27 밤)

## 왜
- 122B는 bf16이 244GB라 G4(96GB)·A100(80GB)에서는 학습할 수 없었다. MoE 전문가 층 때문에 4bit 학습도 안 된다. 그래서 GPTQ 4bit zero-shot(검증 96.0%)만 돌렸다.
- B300 1장(288GB)이면 bf16 LoRA가 들어간다. Unsloth 기준으로 122B-A10B bf16 LoRA에는 256GB가 필요하다.
- 기대치
  - zero-shot 96.0%에 학습 이득 +1.1~1.4%p를 더하면 단독 약 97.1~97.5%로 본다.
  - 같은 Qwen3.5 계열이라 앙상블 이득은 작을 수 있다.
  - 1등을 목표로 시도하기로 했다.
- 초대형 후보를 따져 본 결과
  - Kimi-K3(2.8T), Kimi-K2.x(1T), DeepSeek-V4.1-Flash(763B), MiniMax-M3(428B), GLM-5.3-Flash(320B)는 RunPod 한 pod의 최대 메모리(576~705GB)로는 학습이 안 된다. zero-shot만 가능하다.
  - DeepSeek-V4 Flash·Pro는 텍스트 전용이다.
  - OCRBench 순위: Kimi K2.5 92.3, Qwen3.5-122B 92.1, Qwen3-VL-235B 92.0. 122B가 이미 최상위권이다.

## 파일
- `runpod_q35_122b_bf16.ipynb`: RunPod Jupyter용. stage2_newfam에서 만들었고, 학습·평가·제출 코드와 결과 파일 이름은 그대로다.
  - 0번(새): 환경 점검. 확인 항목:
    - GPU 메모리 합계 250GiB 이상
    - 드라이버 575 이상
    - `/workspace` 남은 공간 300GB 이상
    - 컨테이너 디스크 15GB 이상
    - `HF_HOME=/workspace/hf`로 설정
  - 2번: 설치.
    - torch가 CUDA 12.9 미만이면 cu130 휠로 바꾼다(드라이버 580 미만이면 cu129). B300은 CUDA 12.9 이상이 필요하다.
    - torchaudio·torchao를 지운다.
    - torch 버전을 고정한 채 transformers 5.17.0 · accelerate 1.15.0 · peft 0.21.0 · flash-linear-attention 0.5.2를 설치한다.
    - `USE_FLA=False`면 fla를 빼고 설치한다.
    - 7z가 없으면 apt로 설치한다.
    - 새 프로세스에서 import를 점검한다.
  - 3번: HF 비공개 데이터셋 저장소(`<아이디>/ssafy-vqa-private`)에서 zip을 받아 7z(없으면 unzip, 그것도 없으면 zipfile)로 푼다.
  - 3-1번(새): `snapshot_download`로 가중치 244GB를 받는다.
  - 7번: GPU가 2장 이상이면 `device_map="auto"`로 나눠 올린다(B200 2장 대비). 로드 후 GPU 메모리를 출력한다.
  - 8·10번: 진행을 `RUN_DIR/progress.log`에 적는다. 해상도별 채점 속도(첫 배치 제외)와 학습 스텝 시간(첫 스텝 제외)을 기록한다.
  - 9번: 손실 계산 때 정답 텐서를 로짓과 같은 GPU로 옮긴다.
  - 10번: 본 실행에서 zero-shot 300문항이 93% 미만이면 학습 전에 멈춘다.
  - 10번: DRY_RUN 끝에 본 실행 전체의 예상 시간·비용표를 보여 준다. 항목:
    - 가중치 로드
    - zero-shot
    - 학습 357스텝
    - 빠른 검증 3번
    - epoch 끝 검증
    - 최종 up2.0 검증
    - test 6,714
    - 비용 = 시간 × `GPU_PRICE_PER_HOUR`
  - 14번(새): 결과를 HF 비공개 저장소 `vqa_runs/<RUN_NAME>/`로 올린다.
    - 올리기 전 점검: 검증 1,000 · test 6,714 · 확률 열 · `train_log` MODEL_ID · 어댑터, 저장소가 비공개인지
    - `ckpt_last`는 올리지 않는다.
    - DRY_RUN 결과는 올리기를 거부한다.
- `runpod_bridge_colab.ipynb`: Colab CPU용.
  - A: Drive zip을 비공개 저장소에 올린다. 같은 크기면 건너뛰고, 공개 저장소면 멈춘다.
  - B: 결과를 Drive `vqa_runs/<RUN_NAME>/`로 받는다. 파일 이름·문항 수·열, `valid_ids.csv`와의 분할 일치를 점검한다.
  - C: 저장소 삭제(기본은 끔).
- 사용 가이드: 별도 문서 "RunPod 122B 학습 가이드"(이 저장소에는 없음). 가입, pod 설정(B300 1장, Container 50GB, Volume 600GB, 환경 변수 HF_TOKEN), DRY_RUN → 본 실행, 결과 받기, Terminate, 문제 해결 표를 담았다.
- 실행 이름: `q35_122b_a10b_r16_native_bf16`. 레시피는 Q35와 같다(LoRA r16/α32, native 학습 1 epoch, 유효 배치 16, up2.0 평가).

## 비용·시간 (추정)
- B300 1장: Secure $7.89/시간, Community $6.94/시간.
- 준비(설치·다운로드) 30~60분 + 본 실행 2~4시간 → 약 $25~40. 정확한 값은 DRY_RUN 예상표에 나온다.
- 근거
  - G4 실측: Q35-27B 4bit 12.3초/스텝, up2.0 추론 0.88초/문항.
  - 122B는 한 토큰에 활성 파라미터가 10B라 계산이 27B의 약 0.4배다. B300은 G4보다 4~5배 빠르다.
  - transformers MoE 학습은 이론 계산값보다 3~7배 느리다고 보았다.
- B300이 없으면 B200 2장($13.58/시간)을 쓴다. 층을 나눠 올려서 속도는 1장과 비슷하다.

## 점검 (CPU)
- 시험 모델: 작은 qwen3_5_moe와 실제 Qwen3VLProcessor로 만든 가짜 "Qwen/Qwen3.5-122B-A10B".
- 가짜 HF 허브를 썼고, 비밀번호 zip과 실제 `/workspace` 경로로 돌렸다.
- 전체 흐름 29개 점검 통과. 순서:
  1. 브리지 A: zip 올리기, 다시 실행하면 건너뜀, 공개 저장소면 멈춤
  2. DRY_RUN
     - 데이터 받기·풀기, 분할 md5
     - 예상표 합계를 독립 계산과 대조
     - progress.log 기록
     - 올리기 거부
  3. 게이트: zero-shot < 기준 → 학습 전에 멈춤
  4. 2스텝에서 중단 → 이어서 끝까지
  5. 올리기: 체크포인트 제외, 바이트 단위 일치
  6. 브리지 B: 분할 대조, 다른 분할이면 멈춤
  7. ens_search 1~5번 셀이 새 멤버로 찾음: 계열 Qwen/Qwen3.5-122B-A10B, up2.0, test 확률 일치
- 0번 셀 시나리오 6개(B300 1장·B200 2장 통과 / H100·드라이버·볼륨·컨테이너 부족은 멈춤)와 2번 셀 시나리오 5개(torch cu130·cu129·그대로 / import 실패 / USE_FLA=False) 통과.
- 실제 Jupyter 커널로 두 번 실행해 통과했다: DRY_RUN → 14번 거부, 새 커널에서 본 실행 → 올리기.
- 시험하지 못한 것: 실제 B300에서의 속도·메모리, fla Triton 커널의 SM103 동작, 244GB 로드. 모두 DRY_RUN에서 드러난다. fla가 안 되면 `USE_FLA=False`로 바꾼다.
