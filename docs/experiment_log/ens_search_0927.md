## 무엇
- manual_ensemble과 같은 멤버 탐색을 한 뒤 다음 실행을 뺀다.
  - `_full` 실행: 이름을 `_`로 나눈 조각에 `full`이 있거나, train_log에 `TRAIN_ON_FULL`이 있는 실행
  - 검증이 99%를 넘는 실행: 검증을 학습에 쓴 것으로 본다
- 남은 실행(test 예측까지 있는 것)으로 좋은 조합을 찾는다. CPU만 쓴다.
- 결합 설정 3가지(확률 평균 / 확률+멤버별 온도 / 로그확률 평균)마다 검색 방법을 돌린다.
  1. **전수**: 같은 가중치 부분집합을 모두 계산한다. 조합 수가 `MAX_SUBSETS`(기본 100만)를 넘으면 조합 크기를 줄인다. 후보로 올리는 것:
     - 정확도→NLL 1위
     - NLL 1위
     - **합의 조합**: 상위 100개에 가장 자주 든 실행을 그 조합들의 크기 중앙값만큼 모아 같은 가중치로
  2. **그리디**(Caruana): 가중치 1씩 최대 25번 더하고, 가장 좋았던 시점을 쓴다.
  3. **좌표 상승**: 기준 조합에서 시작해 실행 하나씩 가중치 {0, 0.5, …, 3}을 바꿔 가며 올라간다.
- **중첩 CV**(5겹 × 4번): 800문항으로 검색하고 남은 200문항으로 채점한다.
  - 방법 × 설정마다 다음을 보여 준다:
    - '검증(%)': 1,000문항 전체로 고른 값
    - '중첩 CV(%)'
    - '과대평가(%p)'
    - 기준 대비 CV 고침 / 새로 틀림
  - '모든 방법 중 최고 고르기'도 하나의 방법으로 채점한다.
  - 전수 검색은 한 번 훑을 때 fold별 최고와 fold별 상위 100개까지 같이 구한다. 그래서 CV 때문에 시간이 더 들지 않는다.
- 후보 표에 나오는 것:
  - 검증, NLL
  - 기준 대비 고침 / 새로 틀림 / p
  - `_full` 칸 · `_full`로 바뀐 답 (아래 절)
  - test 답이 기준·majority_vote·clean4와 다른 수
  - 저장 가능 여부
- 결과 파일과 패널:
  - `ens_search/search_<시각>_cv.csv`, `_candidates.csv`, `.json`으로 남는다.
  - 10번 패널에서 후보를 불러와 슬라이더로 다듬을 수 있다. 슬라이더로 고친 뒤 저장하면 이름에 '수정'이 붙는다.
  - 저장하면 `ens_search/submission_*.csv`와 설정 JSON이 생긴다. 검색 후보면 JSON에 그 방법의 CV 기록도 들어간다.
  - 13번 셀: JSON만으로 다시 만들어 저장본과 같은지 확인한다.
  - 14번 셀: 제출끼리 비교한다(`manual_ens` 저장본 포함).

- 중첩 CV가 기준 조합의 검증보다 높고, CV 고침이 새로 틀림보다 뚜렷이 많을 때만 그 방법이 낫다고 본다.

  - 새 멤버(OCR Gemma, 122B 제로샷 등)가 들어간 뒤 같은 잣대로 다시 보는 도구다.

## 제출 파일에 `_full` 섞기 (FULL_MODE, 0927 저녁 추가)
- **원칙**: 검색·검증·중첩 CV는 항상 `_full` 없이 한다. `_full`은 검증 문항으로 학습해서 검증으로 잴 수 없다. `_full`은 제출 파일(test 답)을 만들 때만 쓴다.
- **1번 셀 설정**
  - `FULL_MODE = "mix"`: 기본값. 짝이 있는 멤버의 test 확률을 (원래 + `_full`) / 2로 바꾼다.
    - `"swap"`은 `_full`로 교체한다(E8 방식, 공개 −4였지만 잡음 범위).
    - `"none"`은 섞지 않는다.
  - `FULL_PAIRS`: 이름 규칙(`<멤버>_full`) 밖의 짝.
    - 기본으로 `q3vl_32b_old_up15 → q3vl_32b_r16_native_full`이 들어 있다.
    - bf16 멤버(gemma up20 bf16, q35 bf16)를 4bit `_full`과 짝짓는 줄은 주석으로 넣어 두었다. 학습 설정이 달라서 기본으로는 끄고, 쓸지는 직접 고른다.
  - `FULL_MIN_AGREE = 97.0`: 짝의 test 답이 원래 실행과 97% 이상 같아야 하고, train_log에 `TRAIN_ON_FULL`이 있어야 쓴다.
- **표시되는 곳**
  - 5번 셀: 짝마다 일치율과 통과·거부를 출력하고, 멤버 표에 `_full` 칸이 생긴다.
  - 9번 후보 표
    - `_full` 칸: 섞는 방식과 짝 있는 멤버 수.
    - `_full로 바뀐 답` 칸: `_full` 때문에 바뀐 test 답 수.
    - `기준 clean4_qg_hcx` 줄은 지금 제출 그대로(`_full` 없이)이고, 재현 점검용으로 `test≠clean4 = 0`이어야 한다.
    - `기준 + _full mix` 줄을 새로 더했다.
    - 검색 후보는 모두 FULL_MODE로 test 답을 만든다.
  - 10번 패널: 'test' 메뉴가 생겼다.
    - 후보를 불러오면 그 후보의 설정을 따른다. 버튼으로는 바뀌지 않는다.
    - '코드로 출력'에 FULL도 나온다.
  - 11번 셀: `FULL = FULL_MODE` 변수가 생겼다.
    - PICK 후보에도 이 값을 쓴다.
    - 후보와 설정이 다르면 이름에 `· test none` 같은 꼬리가 붙는다.
    - 검색 기록(NOTE)은 그대로 JSON에 남는다.
- **저장·재현**
  - JSON의 멤버 칸에 섞은 `_full` 파일 경로와 md5(`full_test`, `full_test_md5`)가 남는다.
  - 13번 재현 점검은 그 파일로 다시 만들고, `_full` 파일이 나중에 바뀌면 경고한다.
  - 설정이 바뀌면 파일 이름 끝의 해시도 바뀐다.
- **실제 데이터에서 주의할 점**
  - Drive의 `_full`은 4개다: gemma4_31b_r16_up20, q35_27b_r16_native, q38_27b_r16_native, q3vl_32b_r16_native. 모두 4bit 설정의 짝이다.
  - 공개 최고 조합(ea0e9f)에서 이름 규칙으로 섞이는 멤버는 q38_27b_r16_native 하나뿐이다(그 `_full`에 test 예측이 있을 때). 나머지 멤버는 이렇다:
    - gemma bf16, gemma OCR bf16, ivl35, q35 bf16에는 자기 `_full`이 없다.
    - bf16 멤버에도 섞으려면 FULL_PAIRS의 주석을 풀거나, 그 설정 그대로 `TRAIN_ON_FULL` 학습을 새로 해야 한다.
- **검증**
  - 시나리오: main · valonly · noref · modes(swap/none) · pairs(FULL_PAIRS) · timing이 모두 통과했다.
  - main: 후보 29개의 `_full` 칸, 바뀐 답, test 차이를 섞기까지 포함한 독립 계산과 대조했다.
  - 저장 6개가 재현에서 모두 같았고, `_full` 파일 변조를 감지했다.
  - pairs:
    - 이름이 다른 짝(해상도 up1.5)은 통과했다.
    - 다른 모델과의 짝(94.7%)은 거부했다.
    - 기본 짝을 덮어쓰는 경우(96.0%)는 거부했다.
    - flag가 없으면 거부했다.
  - 실제 ipykernel 실행도 통과했다(패널 test 메뉴·저장·재현 포함).
