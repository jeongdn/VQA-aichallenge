# E17 (제안 번호) — PaddleOCR-VL 글자를 프롬프트에 넣어 Qwen3.5-27B · Gemma4-31B 재학습 (2026-09-27)

## 왜
- E14 조합의 검증 오답 24개 중 **진짜 모델 실수 6개**(1,000문항 중 0.6%)는 대부분 "이미지 글자를 그대로 읽으면 풀리는" 문항이다.
  - 2112 출구 안내판 배치
  - 0936 작은 요금표
  - 5797 거꾸로 붙은 스티커
  - 5209 작은 글씨 100g
  - 1045 철자 틀린 보기
  - 1000 "미술랭투스타"
- 멤버들이 같은 오답을 확신하는 구조라, 입력 자체(글자 정보)를 바꾸는 것이 남은 방법 중 하나다.

## 설계
1. **`ocr_paddle.ipynb`**
   - PaddleOCR-VL-1.6(0.9B, Apache-2.0, transformers 5.17 기본 지원)으로 train 6,714 + test 6,714장에서 한 번 글자를 뽑는다.
   - 작업은 `Spotting:`(글자 줄 + 4점 위치). 공식 전처리를 따른다: 1500px 미만이면 2배 LANCZOS, 최대 픽셀 2048×28×28.
   - 결과는 `vqa_runs/ocr_paddle/pvl16_spotting/ocr_text.csv`(줄마다 `[위치 태그, 글자]`, 위→아래·왼→오른 정렬, 반복 줄 제거).
   - 샤드(`NUM_SHARDS`, `SHARD_ID`)로 여러 GPU에 나눠 돌리고, 끊기면 이어서 진행한다. T4는 float32로 돈다.
   - 8번 점검 셀에서 확인할 것:
     - OCR만으로 보기 고르기 정확도
     - 정답 보기 문자열이 OCR에 통째로 있는 비율 vs 오답 보기 비율
     - E14 오답 24개의 OCR 원문
2. **`stage2_ocr_qwen35.ipynb` / `stage2_ocr_gemma4.ipynb`**
   - 팀의 bf16 stage2 레시피를 그대로 쓴다(Qwen: native·MICRO_BS 2×8 / Gemma: up2.0·1×16, LR 1e-4, 1 epoch, r16).
   - 바뀌는 것은 프롬프트뿐이다:
     - user = 이미지 → `[이미지 속 글자 — OCR 자동 인식 결과. 틀리거나 빠진 글자가 있을 수 있음]` + "(위 왼쪽) 글자" 줄들 → 질문 → 보기 → 답 지시.
     - 학습·검증·test가 모두 같은 형식이다.
     - 1,000자를 넘으면 질문·보기와 겹치는 줄을 우선으로 남긴다(원래 순서 유지).
   - 실행 이름: `q35_27b_r16_native_ocr_bf16`, `gemma4_31b_r16_up20_ocr_bf16`. `MAKE_SUBMISSION=True`라 검증과 test 예측이 함께 나온다(E14가 자동으로 잡음).
   - 11-2 셀: OCR 없는 같은 레시피(`*_bf16`, 원래 4bit 실행)와 같은 문항 비교를 한다.
     - 고침 / 새로 틀림 / 부호 검정
     - E14 오답 24개에서 맞힌 수
   - E14는 계열을 MODEL_ID로 묶으므로 이 실행들은 OCR 없는 같은 모델과 같은 계열이 된다. 조합 판단은 팀이 한다.

## 실행 순서
1. `ocr_paddle.ipynb`
   - 기기 2대면 `(NUM_SHARDS, SHARD_ID) = (2, 0)`과 `(2, 1)`로 동시에 실행한다.
   - 모두 끝나면 한쪽에서 7·8번 셀을 다시 실행해 `ocr_text.csv`를 만든다.
2. `stage2_ocr_qwen35.ipynb`와 `stage2_ocr_gemma4.ipynb`를 각각 다른 GPU에서 전체 실행한다 (DRY_RUN 먼저 권장).
3. 11-2 셀 결과 + E14 재실행으로 판단한다.

## 점검 (CPU, 실제 transformers 5.17 구조의 작은 무작위 모델)
- **OCR 노트북:** 작은 PaddleOCR-VL + 실제 프로세서(1.6판 채팅 템플릿)로 5개 시나리오 통과.

  - 파싱 결과를 설계값과 대조 (400장): 위치 태그, 정렬, 반복 제거, 잘린 줄, EOS 제거
  - 점검 수치를 독립 계산과 대조

  - 전체 흐름 / DRY_RUN / OCR 누락 시 학습 전 중단
  - 검사 항목:
    - OCR 블록 형식, 빈 OCR 처리
    - 긴 OCR 줄이기: 정답 줄 유지 + 순서 유지
    - 선지를 섞어도 OCR 블록이 같음
    - 학습 기록의 OCR 설정, 오답 리포트의 OCR 표시
    - 비교 셀 수치를 독립 계산과 대조, 제출 파일
    - Gemma 레시피 유지

## OCR 결과 점검 (2026-09-27 05시, 8번 셀, 검증 1,000문항)
- **전체 수치**
  - 13,428장 완료. 글자 없음 3.0%, 상한(512토큰) 도달 25.2%.
  - 상한 도달의 상당수는 생성 루프다(예: "1000…", 같은 줄 반복). 학습 노트북 v2에서 불러올 때 정리한다.
  - 검증에서 OCR이 있는 문항: 967개.
  - 정답 보기 문자열이 OCR에 통째로 있음: 34.0%. 오답 보기(셋 중 하나라도)가 통째로 있음: 16.9%.
  - OCR만으로 고르기: 결정 54.2%, 결정한 문항의 정확도 76.2%, 전체 기준 41.3%.
- **진짜 모델 실수 6개**
  - 1000: OCR "미술랭투스타신정" → a 0.71 vs b 0.17. 결정적 단서 있음.
  - 1045: TAMARINDO·JAMAICA는 정확히 있고 TANARINDO는 없음 → 부정형 정답과 맞음. 부분 단서.
  - 2112: "서교동 방면"과 위치 태그는 있으나 출구 번호 연결은 불확실.
  - 0936: 요금표 못 읽음.
  - 5209: "109g"로 잘못 읽음.
  - 5797: 거꾸로 붙은 스티커를 못 찾음(0줄).
  - 정리: 단서가 있는 것은 1~3개.
- **라벨 오류·애매 문항**
  - OCR은 대체로 기존 모델의 답 쪽을 지지한다(0175 ROCK, 1785 기적 등). 라벨 문제는 OCR로 풀리지 않는다.
- **남는 잡음**
  - 변형이 섞인 반복 줄(5008 "참급/카드 동일조건" 10여 줄).
  - 수식 환각(2112의 `\( \alpha \beta … \)`).
  - 자모 조각(1900 "ㅌㅊㅊㅊㅇㅇ…").
  - 정확히 같은 반복과 긴 반복만 정리되고, 이런 것들은 그대로 들어간다.

## 학습 결과 판정 (2026-09-27 10시, 11-2 셀 출력 기준)
- **Gemma OCR** `gemma4_31b_r16_up20_ocr_bf16`: 검증 97.70%.
  - vs 4bit 97.60%: 고침 6 · 새로 틀림 5 (p=1.0)
  - vs bf16 97.50%: 고침 5 · 새로 틀림 3 (p=0.73)
  - 라벨 오류 10개를 빼면 4bit 대비 +1, bf16 대비 +3.
- **Q35 OCR** `q35_27b_r16_native_ocr_bf16`: 검증 96.90%.
  - vs 4bit 97.20%: 고침 4 · 새로 틀림 7
  - vs bf16 97.10%: 고침 4 · 새로 틀림 6
- **재학습 흔들림과 비교** (고침/새로 틀림 목록에서 역산):
  - OCR 없는 4bit와 bf16끼리도 맞고 틀림이 갈리는 문항이 Gemma 11개, Q35 7개다.
  - Gemma OCR과 기준의 차이(8·11문항)는 이 흔들림과 같은 크기다.
  - Q35 OCR과 기준의 차이(10·11문항)는 흔들림보다 약간 크고, 손해 쪽이다.
- **두 기준이 같은 결과를 낸 문항만 보면**:
  - Gemma: 고침 3(2732 500원 상품 · 4439 건물 이름 · 4872 이름표) · 새로 틀림 1(6511) → +2
  - Q35: 고침 2(4663 · 6117) · 새로 틀림 5(0024 · 0356 · 4439 · 5041 · 5763) → −3
  - 4439 · 5041은 같은 OCR 글자를 받고 Q35 OCR은 둘 다 틀리게, Gemma OCR은 둘 다 맞게 바뀌었다.
- **E14 오답 24개**: Gemma OCR 8개. OCR 없는 Gemma도 4bit 7개 · bf16 8개를 맞힌다. Q35는 판에 따라 1~3개.
  - 이 문항들을 조합이 못 고친 것은 Gemma가 조합 안에서 소수파이기 때문이다. OCR 효과가 아니다.
- **진짜 실수 6개에서 OCR 효과는 0이다.**
  - 0936 · 1000 · 1045: Gemma 세 판이 모두 맞힌다.
  - 5797: bf16만 맞힌다. OCR이 0줄을 읽은 문항이다.
  - 5209: 4bit만 맞힌다. OCR이 109g로 잘못 읽은 문항이다.
  - 2112: 세 판 모두 틀린다.
  - Q35 OCR은 결정적 단서가 있는 1000도 틀렸다.
- **판정**
  - 단일 모델 이득은 흔들림 범위 안이다.
  - Gemma OCR은 조합 후보로만 둔다. manual_ensemble에서 `gemma4_31b_r16_up20_ocr_bf16 넣기`를 대조군 `gemma4_31b_r16_up20_bf16 넣기`(같은 레시피, OCR 없음)와 비교해 판단한다.
  - OCR을 다른 계열(Q38 · HCX)로 넓히지 않는 것을 권한다.
